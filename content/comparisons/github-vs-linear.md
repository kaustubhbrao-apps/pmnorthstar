**[GitHub](/case-study/github-polish-as-marketing) owns software's past — the commits, the pull requests, the entire history of what was built. [Linear](/case-study/linear-brand-from-day-one) owns software's future — the tickets, the cycles, the plan for what gets built next. They are complementary by design, which makes their overlap at the edges the whole story: GitHub, where the code already lives, exerts a gravity that pulls adjacent tools toward it, while Linear bets that developers will pay a premium for a markedly better experience even when an adequate alternative comes free with their repository. It is a contest between the pull of the incumbent and the pull of craft.**

Which force wins is one of the defining questions in developer tools, because it decides whether "good enough and bundled" beats "excellent and separate."

## Two different centers of gravity

GitHub, launched in 2008 on a social layer atop Git, became the place developers keep their professional identity — open source, portfolio, the code of an entire career. That created a network effect no prior developer tool had achieved, and Microsoft paid $7.5 billion in 2018 for what it correctly read as critical infrastructure. Linear, launched in 2019, started from a universal frustration: issue tracking was uniformly bad — Jira powerful but slow, GitHub Issues lightweight but thin, Trello visual but not built for how software teams work. Linear's thesis was that project management should feel like a code editor: keyboard-first, sub-100ms, opinionated rather than infinitely configurable. Engineering teams responded with NPS scores rivaling the best consumer products ever shipped. One company owns where the work is stored; the other owns how the work feels.

## The overlap is where the tension lives

The friction is specific. GitHub Issues handles bug reports, requests, and tasks tied directly to repositories; Linear handles the same jobs with dramatically better speed, visualization, and workflow. Many teams run both — Linear to plan and manage cycles, GitHub to review code and run CI — and the integration is tight enough that merging a PR can update a Linear ticket automatically. But GitHub is steadily extending into project management, and it does so from the structurally advantaged position of already holding the code. That is the gravity well: a tool that lives next to the repository starts with distribution the challenger has to earn from scratch.

## Incumbent gravity versus the craft premium

So the existential question for Linear is clean: will teams pay for world-class project management when a free, adequate version ships with their code host? The evidence so far is yes — Linear has grown rapidly through exactly the period in which GitHub Projects improved substantially, which suggests the experience gap is wide enough that developers notice and choose it. But the long game favors Microsoft, which can afford to build and give away developer tooling in service of a broader enterprise strategy that does not need the tool itself to be profitable. Linear's entire bet is that the people who build software care enough about how they experience that work to keep paying for the best tool regardless of what comes bundled. It is a bet on craft outrunning convenience.

## What this means for operators

- **Know whether you own the system of record or the system of experience.** GitHub's moat is that the code lives there; Linear's is that the work feels better there. The first resists displacement; the second must continually re-earn the premium.
- **Bundling is a distribution weapon, not a quality claim.** An incumbent adding your feature for free wins on gravity, not excellence. If you are the challenger, your margin of safety is the size of the experience gap — protect and widen it.
- **A craft premium is real but conditional.** Teams will pay for the best tool as long as "best" is obviously better. The day the free bundled option becomes merely good enough, the premium evaporates. Stay far enough ahead that the comparison is never close.
